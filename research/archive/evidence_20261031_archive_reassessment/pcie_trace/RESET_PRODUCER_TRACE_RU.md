# Статическая трасса reset-list producer/filter (offline)

## Основной вывод

Найден один конкретный producer path для `SimGpuDev` (это не полный перечень producers): функция с `.eh_frame` FDE `0xebf500..0xec00c9` загружает global reset-list `0xf7a7fb8`; её call-site `0xebf9ee` передаёт этот global в append-helper `0xe125f0`. Helper записывает 16-byte запись в primary vector контейнера (`begin/end/capacity` at `+0x28/+0x30/+0x38`), а при заполнении вызывает grow-helper `0xe12320` с `container+0x28`. Второй helper call-site `0xebfee4` не подтверждён как запись в reset global.

Построенная запись видимого второго call path — pointer на объект, созданный в текущем FDE, плюс reference-counted control-block pointer: `0xebf954` ставит объекту vptr `0x4c5a768`; `0xebf993` пишет его адрес в первый qword временной 16-byte записи; allocator result записывается во второй qword на `0xebf9b5`. RTTI имена связывают vptr container `0x4c4b6e8` с `TestDeviceMgr`, candidate object vptr `0x4c5a768` — с `NvLinkDevIf::SimGpuDev`, control-block typeinfo — с `std::_Sp_counted_ptr<NvLinkDevIf::SimGpuDev,...>`. Это точный типовой статический provenance; `SimGpuDev` не равен доказательству физического GPU/BDF.

Producer выполняет фильтрующие проверки до append: перебирает существующий primary list и получает элементы через accessor `0xe110d0`; перед дальнейшей обработкой проверяет cast/helper `0x4666580`, вызывает candidate virtual slot `+0x210` с opaque global argument pointer `0xfa85850`, имеет дополнительную условную проверку slot `+0x180` под flag bit `[r13+0x84]`, затем проверяет тип/методный слот `+0x130` и связанный объектный путь. Отдельно в построении нового SimGpuDev проверяется dynamic method slot `+0x268 == 0x756ea0`, прежде чем его `+0xd8` получает `r15d` и запись добавляется. Это конкретные predicates, но тип и назначение global argument pointer `0xfa85850`, а также смысл `r15d` в данном source slice не установлены. Input в RSI при входе — vector-like begin/end: function entry сохраняет RSI в R14, а затем трактует `[RSI]` и `[RSI+8]` как границы 16-byte records. Следовательно, producer использует device-like records/objects из переданного input, однако происхождение этого аргумента выше по стеку пока не связано с конкретным CLI filter. В просмотренном FDE нет доказанного сравнения PCI BDF или явного `-only_pci_dev` filter. Поэтому нельзя заключить, что producer фильтрует по BDF либо что runtime reset list ограничен exact target.

Для direct-call inventory выполнен потоковый поиск кодирования `CALL rel32/JMP rel32` на target `0xe125f0` в RX PT_LOAD: найдено два CALL (`0xebf9ee`, `0xebfee4`), но они не эквивалентны. На первом call RDI=RBX, а RBX всё ещё указывает на global `0xf7a7fb8`, загруженный на `0xebf55b`; RSI указывает на локальную candidate pair. Между этим call и вторым в alternate construction path `0xebfa95` перезаписывает RBX адресом новой allocation; следовательно, для `0xebfee4` нельзя утверждать RDI=`0xf7a7fb8` без отдельного CFG proof. Этот второй call не засчитан как append в reset global. Потоковый byte scan доказывает только эти два direct rel32 encodings, не исключает indirect dispatch/другой encoding.

## Consumer vs producer: отдельные методы

`0xe12010` — vtable slot `+0x30` у `TestDeviceMgr`. Его **полный основной code range** просмотрен от `0xe12010` до exclusive FDE end `0xe12317` (код cleanup заканчивается `0xe12315`); следующая функция начинается `0xe12320`. Метод читает primary list `this+0x28`, проходит 16-byte entries и вызывает virtual методы на первом qword; его vector growth/append код относится к вторичному integer vector `this+0x40`. Он не является append-helper primary vector. Primary append находится отдельно в `0xe125f0`.

`0xe11af0` constructor устанавливает `TestDeviceMgr` vptr и обнуляет обе vector triples: primary `+0x28/+0x30/+0x38`, secondary `+0x40/+0x48/+0x50`. Caller `0x746909..0x74691e` создаёт и публикует этот контейнер, затем вызывает `0x742690`; позже `0x746957` вызывает `TestDeviceMgr+0x30`, а в цикле `0x746977` вызывает другой object `+0x30`.

`0x742690` остаётся отдельным generic registry/property callback path: обращается к global registry `0xf7aab30`, проверяет режим через `0x5f5030`, затем проходит `0x73f9a0`, `0x61a580`, `0x61bef0`. В ограниченном теле нет literal `0xf7a7fb8`, container offsets или direct call `0xe125f0`; косвенные эффекты через generic bridge нельзя исключить. Теперь producer найден в ином FDE, поэтому смешивать callback path с прямым append evidence не следует.

## Replay and limits

`reset_producer_replay.py` streams SHA-256 in 1 MiB blocks, then performs bounded seek/read checks for the load, both call encodings, primary append/grow instructions, constructor fields and type names. PASS receipt: `RESET_PRODUCER_REPLAY.json`. Disassembly used bounded `objdump` windows only. The ELF was not executed; no hardware, SSH, reset, MMIO, build or scripts from the source corpus were run.

This establishes one static `SimGpuDev` producer path and candidate type shape, not all possible producer paths and not runtime list population on the last paused run. The predicates include virtual/indirect paths; the opaque global argument pointer `0xfa85850` has untraced type and purpose and does not identify a BDF. No claim is made that `-only_pci_dev` filters this list, that all listed entries are physical devices, or that any reset was requested/executed. The x16 hardware goal remains paused.
